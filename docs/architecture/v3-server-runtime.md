# Серверный runtime v3 для Android и Windows

Срез реализации: 10 ноября 2026 года. Android и Windows используют общий Java-клиент из `backend/client`, а не запускают Swift-пакет `BlotWorkspace`. DTO по-прежнему генерируются из `contracts/v3/model.json`; приложения компилируют эти исходники с Java 17 без копирования моделей.

## Рабочие операции

Авторизованный `GET /v3/compatibility` возвращает версию, владельца, workspace и точный список команд. Сейчас реализованы `agent.save`, `conversation.create`, `conversation.send_message`, `conversation.update`, `conversation.delete`. Поддерживается личный текстовый чат с существующим `ProviderGateway` и его настройками провайдера. Новые агенты не получают инструменты и не запускают внешние действия.

`POST /v3/commands` возвращает квитанцию ACCEPTED, а не результат выполнения модели. `GET /v3/commands/{commandId}` позволяет сверить неопределённый исход отправки. Сервер нормализует владельца, workspace, версии, даты и порядок сообщений. Одна транзакция фиксирует записи, события и квитанцию. Повтор идентичной команды возвращает прежнюю квитанцию; повтор идентификатора с другим содержимым даёт 409. Изменение записи требует актуального expectedVersion. Другой аккаунт не видит запись или квитанцию.

`GET /v3/snapshot?cursor=...&limit=100` возвращает schemaVersion=3, sequence, records и nextCursor. Лимит — 1–500 записей. Курсор удерживает watermark: история ревизий обеспечивает согласованные страницы даже при последующих изменениях и удалениях. `GET /v3/events?after=...` передаёт SSE-уведомления об ID и версии записи с heartbeat каждые 15 секунд. После события клиент перечитывает подтверждённые данные. Java-клиент пока обновляет snapshot опросом; поток доступен другим потребителям.

## Хранение и восстановление

База `<blot.database>.v3.db` создаётся рядом с прежней базой, отдельно от v2. Старые данные не преобразуются и не удаляются. Повторное открытие сохраняет квитанции, историю ревизий и очередь ответов. Ответы SAVED можно начать после перезапуска. RUNNING становится INTERRUPTED: неизвестный внешний вызов модели не повторяется автоматически. Ошибка провайдера сохраняется как FAILED, а не как успешный ответ. Удаление чата также скрывает его сообщения и предотвращает восстановление удалённого ответа работающим worker.

## Подключение

Используется действующая bearer-сессия существующего локального backend. На Windows клиент может обращаться к HTTP loopback; для соединения с другого устройства нужен HTTPS с доверенным сертификатом и сессия сопряжённого устройства. Сессия локального компьютера не даёт удалённому устройству доступ: существующий SessionService продолжает проверять это ограничение. Токен вводится в поле сессии приложения, хранится только в памяти и не попадает в URL. Redirect не обрабатывается автоматически. Адрес backend и токен не включаются в коммиты.

Backend запускается существующим способом с настройками BLOT_GIGACHAT_* и SMTP/сопряжения. Для локальной проверки можно использовать `backend/gradlew -p backend :api:bootRun`. HTTP привязан к loopback по умолчанию; настройка удалённого HTTPS и выпуск сессии устройства остаются явными действиями владельца сервера. Эта работа не публикует сервер и не ослабляет TLS-проверки.

## Граница этого среза

Это работающий серверный путь личного чата, а не полный перенос Swift-runtime. Групповой planner, вложения, инструменты/MCP, расписания, lifecycle задач, делегирование, approvals и peer-sync пока не доступны через этот runtime. Их команды возвращают 501; отсутствующие возможности не объявляются работающими и не превращаются в фиктивно успешные задачи. Контракты этих сущностей сохраняются для совместимости. V2 API продолжает работать отдельно.

## Проверки

`V3HttpTest` проходит реальный HTTP-путь с тестовым провайдером: авторизация, агент, чат, сообщение, ответ, повтор commandId, конфликт версии, изоляция аккаунтов, удаление, общий Java-клиент. Отдельная проверка повторно открывает SQLite и проверяет квитанции и согласованную пагинацию. `WorkspaceJsonTest` читает 38 общих fixtures, каталог состояний, старые сообщения без новых полей и недопустимые счётчики. Android APK и Windows installDist проверяются отдельно в ветках адаптации. Проверка на физическом Android-устройстве и реальном аккаунте провайдера требует подключённого устройства и настроенного сервера.
